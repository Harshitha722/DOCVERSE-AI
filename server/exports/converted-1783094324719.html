Q14. What is SAP HANA?

Answer:

SAP HANA stands for High-performance ANalytic Appliance. It is an in-memory, column-oriented, relational database management system developed by SAP.

Key characteristics:

  1. In-Memory Computing: Data is stored in RAM (main memory) instead of traditional disk storage, enabling extremely fast data retrieval and processing
  2. Column-Oriented Storage: Data is stored column-wise rather than row-wise, which dramatically speeds up analytical queries (aggregations, sums, averages)
  3. Row-Oriented Storage: Also supports row-based storage for transactional (OLTP) operations
  4. Combined OLTP + OLAP: Eliminates the need for separate transactional and analytical systems
  5. Data Compression: Advanced compression algorithms reduce memory footprint by up to 10x
  6. Parallel Processing: Leverages multi-core CPUs for parallel query execution

Why HANA matters for ABAP developers:

  • Traditional ABAP code that processes data in application server loops can now push computation to the database
  • New tools: CDS Views, AMDP, Open SQL enhancements
  • Performance gains of 10x to 1000x over traditional approaches

Q17. Explain SAP's 3-tier architecture.

Answer:

SAP follows a 3-tier client-server architecture:

┌─────────────────────┐
│  PRESENTATION TIER  │  ← SAP GUI / Fiori Launchpad (User Interface)
│  (Client Layer)     │
└────────┬────────────┘
         │
┌────────▼────────────┐
│  APPLICATION TIER   │  ← ABAP Application Server (Business Logic)
│  (App Server)       │  ← Contains: Dispatcher, Work Processes, 
│                     │     Memory Buffers, Enqueue Server
└────────┬────────────┘
         │
┌────────▼────────────┐
│    DATABASE TIER    │  ← SAP HANA / Oracle / DB2 (Data Storage)
│  (Database Server)  │
└─────────────────────┘

Tier Details:

  1. Presentation Layer: The user interface — SAP GUI (desktop), SAP Fiori (web browser), or mobile apps. It sends user requests to the application server and displays results.

  2. Application Layer: The core processing engine. Contains:

    • Dispatcher: Distributes incoming requests to available work processes
    • Work Processes: Execute ABAP programs (Dialog, Background, Update, Enqueue, Spool)
    • Gateway: Handles RFC communication
    • Message Server: Load balancing across multiple app servers

  3. Database Layer: Stores all data — master data, transaction data, repository objects (ABAP programs), and customization data.

PART 4 — ABAP Core Programming

Q19. What is ABAP?

Answer:

ABAP stands for Advanced Business Application Programming. It is SAP's proprietary programming language used to develop applications within the SAP environment.

Key characteristics:

  • Event-driven language (programs respond to events like INITIALIZATION, AT SELECTION-SCREEN, START-OF-SELECTION)
  • 4th Generation Language (4GL) — closer to human language than assembly/machine code
  • Runs on the SAP Application Server — not compiled to machine code but interpreted by the ABAP runtime
  • Strongly typed — variables must be declared with specific types
  • Supports both procedural and object-oriented programming
  • Integrated with SAP Dictionary — data definitions are centralized

ABAP Program Types:

Type Code Description
Executable Program 1 Reports (can be run directly via SE38)
Module Pool M Dialog programs (screen-based)
Function Group F Container for function modules
Include Program I Reusable code included in other programs
Class Pool K Global ABAP OO classes
Interface Pool J Global interfaces
Subroutine Pool S Container for subroutines
Type Pool T Global type definitions

Q21. What are Internal Tables in ABAP? Explain types.

Answer:

An internal table is a temporary table that exists in the program's memory during runtime. It's the primary data structure in ABAP for processing collections of data.

Types of Internal Tables

Type Access Duplicate Keys Use Case
STANDARD Index + Linear search Allowed General purpose, most common
SORTED Index + Binary search Depends on UNIQUE/NON-UNIQUE Pre-sorted data, frequent reads
HASHED Hash algorithm Not allowed (UNIQUE only) Large datasets, key-based access

Declaration Examples

" Standard Table
DATA lt_standard TYPE STANDARD TABLE OF mara WITH DEFAULT KEY.

" Sorted Table
DATA lt_sorted TYPE SORTED TABLE OF mara WITH UNIQUE KEY matnr.

" Hashed Table
DATA lt_hashed TYPE HASHED TABLE OF mara WITH UNIQUE KEY matnr.

Key Operations on Internal Tables

" 1. APPEND — Add row to the end (Standard tables)
APPEND ls_row TO lt_table.

" 2. INSERT — Add row at specific position or sorted position
INSERT ls_row INTO TABLE lt_table.

" 3. READ TABLE — Read a single row
READ TABLE lt_table INTO ls_row WITH KEY matnr = '100'.
" Modern syntax:
ls_row = lt_table[ matnr = '100' ].

" 4. MODIFY — Update a row
MODIFY lt_table FROM ls_row INDEX 3.

" 5. DELETE — Remove a row
DELETE lt_table WHERE matnr = '100'.

" 6. LOOP — Iterate over rows
LOOP AT lt_table INTO ls_row.
  WRITE: / ls_row-matnr, ls_row-maktx.
ENDLOOP.

" 7. SORT
SORT lt_table BY matnr ASCENDING.

" 8. CLEAR vs REFRESH vs FREE
CLEAR lt_table.    " Clears content, keeps memory allocated
REFRESH lt_table.  " Same as CLEAR for internal tables
FREE lt_table.     " Clears content AND releases memory

Header Lines (Obsolete but may be asked)

" Old syntax with header line (avoid in new code)
DATA lt_table TYPE TABLE OF mara WITH HEADER LINE.
" The table name doubles as a work area — causes confusion

[!WARNING] Internal tables with header lines are obsolete in modern ABAP. Always use explicit work areas.

Q22. What is the difference between CLEAR, REFRESH, and FREE?

Answer:

Statement Effect on Internal Table Effect on Simple Variable Memory
CLEAR Deletes all rows Resets to initial value Retained
REFRESH Deletes all rows N/A (only for tables) Retained
FREE Deletes all rows Resets to initial value Released
  • Use CLEAR for work areas and variables
  • Use FREE when you're done with a large internal table and want to reclaim memory
  • REFRESH is essentially the same as CLEAR for internal tables

Q24. What is a SELECT statement in ABAP? Explain Open SQL.

Answer:

Open SQL is SAP's database-independent SQL dialect used within ABAP programs. The ABAP runtime translates Open SQL to the native SQL of the underlying database.

Basic SELECT Syntax

" Select single record
SELECT SINGLE matnr, maktx
  FROM mara
  INTO @DATA(ls_material)
  WHERE matnr = '000000000000100'.

" Select multiple records into internal table
SELECT matnr, maktx, mtart, matkl
  FROM mara
  INTO TABLE @DATA(lt_materials)
  WHERE mtart = 'FERT'.

" Select with JOIN
SELECT a~matnr, b~maktx, a~mtart
  FROM mara AS a
  INNER JOIN makt AS b ON a~matnr = b~matnr
  INTO TABLE @DATA(lt_result)
  WHERE b~spras = @sy-langu.

" Select with aggregate functions
SELECT mtart, COUNT(*) AS count
  FROM mara
  INTO TABLE @DATA(lt_counts)
  GROUP BY mtart.

New Open SQL Features (7.40+) — Important for HANA

" Inline declarations with @DATA
SELECT * FROM mara INTO TABLE @DATA(lt_mara).

" String expressions
SELECT matnr, 
       CONCAT( matnr, maktx ) AS combined
  FROM mara INTO TABLE @DATA(lt_result).

" CASE expressions
SELECT matnr,
       CASE mtart
         WHEN 'FERT' THEN 'Finished'
         WHEN 'HALB' THEN 'Semi-Finished'
         ELSE 'Other'
       END AS material_type
  FROM mara INTO TABLE @DATA(lt_result).

" Arithmetic expressions
SELECT matnr, 
       netpr * menge AS total_value
  FROM ekpo INTO TABLE @DATA(lt_result).

" COALESCE, SUBSTRING, etc.
SELECT matnr,
       COALESCE( maktx, 'No Description' ) AS description
  FROM makt INTO TABLE @DATA(lt_result).

Q28. What is a BAPI?

Answer:

BAPI stands for Business Application Programming Interface. It is a standardized function module that provides a well-defined interface to SAP business objects.

Key characteristics:

  • BAPIs are RFC-enabled function modules
  • They follow naming conventions: BAPI_<object>_<method> (e.g., BAPI_SALESORDER_CREATEFROMDAT2)
  • They return errors via a RETURN parameter (structure BAPIRET2)
  • They do NOT commit automatically — you must call BAPI_TRANSACTION_COMMIT or BAPI_TRANSACTION_ROLLBACK
  • They are released and documented by SAP for external use

Common BAPIs:

BAPI Purpose
BAPI_SALESORDER_CREATEFROMDAT2 Create Sales Order
BAPI_PO_CREATE1 Create Purchase Order
BAPI_ACC_DOCUMENT_POST Post Accounting Document
BAPI_MATERIAL_SAVEDATA Create/Change Material Master
BAPI_USER_GET_DETAIL Get User Details
BAPI_TRANSACTION_COMMIT Commit BAPI changes
BAPI_TRANSACTION_ROLLBACK Rollback BAPI changes

Q33. Explain Classes in ABAP with an example.

Answer:

A class is a blueprint that defines attributes (data) and methods (behavior).

" Class Definition
CLASS lcl_employee DEFINITION.
  PUBLIC SECTION.
    " Constructor
    METHODS constructor
      IMPORTING iv_name   TYPE string
                iv_salary TYPE p.

    METHODS get_salary RETURNING VALUE(rv_salary) TYPE p.
    METHODS give_raise IMPORTING iv_percent TYPE p.
    
  PROTECTED SECTION.
    DATA mv_name   TYPE string.
    DATA mv_salary TYPE p DECIMALS 2.
    
  PRIVATE SECTION.
    METHODS validate_salary IMPORTING iv_salary TYPE p
                           RETURNING VALUE(rv_valid) TYPE abap_bool.
ENDCLASS.

" Class Implementation
CLASS lcl_employee IMPLEMENTATION.
  METHOD constructor.
    mv_name   = iv_name.
    IF validate_salary( iv_salary ) = abap_true.
      mv_salary = iv_salary.
    ENDIF.
  ENDMETHOD.
  
  METHOD get_name.
    rv_name = mv_name.
  ENDMETHOD.
  
  METHOD get_salary.
    rv_salary = mv_salary.
  ENDMETHOD.
  
  METHOD give_raise.
    mv_salary = mv_salary + ( mv_salary * iv_percent / 100 ).
  ENDMETHOD.
  
  METHOD validate_salary.
    rv_valid = COND #( WHEN iv_salary > 0 THEN abap_true
                       ELSE abap_false ).
  ENDMETHOD.
ENDCLASS.

Q35. What are Interfaces in ABAP?

Answer:

An interface defines a contract — a set of methods that implementing classes must provide. Interfaces enable polymorphism and decouple design from implementation.

" Interface Definition

  ENDMETHOD.

ENDCLASS.

Q37. What is "ABAP for HANA" or "ABAP on HANA"?

Answer:

"ABAP for HANA" refers to the practice of writing ABAP code that is optimized to leverage the capabilities of the SAP HANA database, particularly its:

  • In-memory computing (data lives in RAM)
  • Column-based storage (fast aggregations)
  • Parallel processing (multi-core optimization)
  • Code-to-data paradigm (push logic to the database layer)

The Code Pushdown Paradigm

Traditional ABAP follows a data-to-code approach:

Database → [Fetch ALL data] → Application Server → [Process in ABAP loops]

ABAP for HANA follows a code-to-data approach:

Database → [Process data WHERE it lives using SQL/CDS/AMDP] → [Return only results]

Why? Because:

  • HANA can process billions of rows in memory in milliseconds
  • Network transfer between DB and App Server is slow
  • Application server loops are sequential; HANA can parallelize

@EndUserText.label: 'Material Master CDS View'

@Analytics.dataCategory: #DIMENSION
@VDM.viewType: #BASIC

  association [0..*] to makt as _Text

{

      meins                    as BaseUnit,

        when 'HALB' then 'Semi-Finished'

Q39. What is AMDP (ABAP Managed Database Procedures)?

Answer:

AMDP allows you to write SAP HANA SQLScript (or other HANA-specific code) inside ABAP class methods. The procedure is managed by the ABAP lifecycle (transport, activation, etc.) but executed directly on the HANA database.

When to use AMDP vs CDS Views

Use CDS Views when... Use AMDP when...
Simple to moderate data models Complex calculations, loops, cursors
Declarative logic suffices Imperative logic needed
Need annotations (Fiori, Analytics) Performance-critical algorithms
Need associations Need temporary tables, variables
Standard reporting Complex string operations, series data

AMDP Syntax

" Class must implement IF_AMDP_MARKER_HDB interface
CLASS zcl_amdp_demo DEFINITION.
  PUBLIC SECTION.
    INTERFACES if_amdp_marker_hdb.
    
    TYPES: BEGIN OF ty_result,
             matnr TYPE matnr,
             maktx TYPE maktx,
             total_stock TYPE p,
           END OF ty_result,
           tt_result TYPE STANDARD TABLE OF ty_result.
    
    " AMDP method declaration
    CLASS-METHODS get_stock_summary
      IMPORTING VALUE(iv_werks) TYPE werks_d
      EXPORTING VALUE(et_result) TYPE tt_result.
      
ENDCLASS.

CLASS zcl_amdp_demo IMPLEMENTATION.
  " AMDP method implementation
  METHOD get_stock_summary
    BY DATABASE PROCEDURE FOR HDB
    LANGUAGE SQLSCRIPT
    OPTIONS READ-ONLY
    USING mara makt mard.
    
    et_result = SELECT 
        a.matnr,
        b.maktx,
        SUM(c.labst) AS total_stock
      FROM mara AS a
      INNER JOIN makt AS b ON a.mandt = b.mandt AND a.matnr = b.matnr
      INNER JOIN mard AS c ON a.mandt = c.mandt AND a.matnr = c.matnr
      WHERE c.werks = :iv_werks
        AND b.spras = 'E'
      GROUP BY a.matnr, b.maktx;
      
  ENDMETHOD.
ENDCLASS.

Key AMDP Rules

  1. Class must implement IF_AMDP_MARKER_HDB
  2. Use BY DATABASE PROCEDURE FOR HDB LANGUAGE SQLSCRIPT
  3. Must list all used tables in USING clause
  4. Cannot use ABAP statements inside the method — only SQLScript
  5. Parameters must use VALUE( ) pass-by-value
  6. Can only be created in Eclipse ADT (not SE24)

AMDP Table Functions (Used in CDS Views)

" AMDP that can be consumed by CDS Views
METHOD get_data 
  BY DATABASE FUNCTION FOR HDB
  LANGUAGE SQLSCRIPT
  OPTIONS READ-ONLY
  USING mara.

  RETURN SELECT matnr, mtart FROM mara;
ENDMETHOD.

Q40. What is Code Pushdown? Give examples of how to optimize ABAP for HANA.

Answer:

Code Pushdown means moving data-intensive operations from the ABAP application server to the HANA database, where they can be executed orders of magnitude faster.

Anti-Pattern 1: SELECT * with Application-Level Filtering

" ❌ BAD — Fetches ALL columns, ALL rows, filters in ABAP
SELECT * FROM mara INTO TABLE lt_mara.
LOOP AT lt_mara INTO ls_mara WHERE mtart = 'FERT'.
  " Process only finished goods
ENDLOOP.

" ✅ GOOD — Filter at database, select only needed columns
SELECT matnr, mtart, matkl
  FROM mara
  INTO TABLE @DATA(lt_mara)
  WHERE mtart = 'FERT'.

Anti-Pattern 2: Nested SELECT (SELECT inside LOOP)

" ❌ BAD — N+1 query problem
SELECT * FROM ekko INTO TABLE lt_ekko WHERE bukrs = '1000'.
LOOP AT lt_ekko INTO ls_ekko.
  SELECT * FROM ekpo INTO TABLE lt_ekpo WHERE ebeln = ls_ekko-ebeln.
  " Process items...
ENDLOOP.

" ✅ GOOD — Single JOIN query
SELECT h~ebeln, h~bukrs, h~lifnr,
       i~ebelp, i~matnr, i~menge, i~netpr
  FROM ekko AS h
  INNER JOIN ekpo AS i ON h~ebeln = i~ebeln
  INTO TABLE @DATA(lt_po_data)
  WHERE h~bukrs = '1000'.

Anti-Pattern 3: Sorting in ABAP

" ❌ BAD — Sort in application layer
SELECT * FROM bseg INTO TABLE lt_bseg WHERE bukrs = '1000'.
SORT lt_bseg BY belnr augdt.

" ✅ GOOD — Sort in database (ORDER BY)
SELECT * FROM bseg 
  INTO TABLE @DATA(lt_bseg)
  WHERE bukrs = '1000'
  ORDER BY belnr, augdt.

Anti-Pattern 4: Aggregation in ABAP loops

" ❌ BAD — Sum in ABAP loop
SELECT * FROM bseg INTO TABLE lt_bseg WHERE bukrs = '1000'.
LOOP AT lt_bseg INTO ls_bseg.
  lv_total = lv_total + ls_bseg-dmbtr.
ENDLOOP.

" ✅ GOOD — Aggregate in database
SELECT SUM( dmbtr ) AS total
  FROM bseg
  INTO @DATA(lv_total)
  WHERE bukrs = '1000'.

Anti-Pattern 5: Using FOR ALL ENTRIES inefficiently

" ❌ BAD — FOR ALL ENTRIES on a large table without checking if it's empty
SELECT * FROM ekpo INTO TABLE lt_ekpo
  FOR ALL ENTRIES IN lt_ekko
  WHERE ebeln = lt_ekko-ebeln.

" ✅ GOOD — Check if driver table is not empty + use JOINs when possible
IF lt_ekko IS NOT INITIAL.
  SELECT * FROM ekpo INTO TABLE @DATA(lt_ekpo)
    FOR ALL ENTRIES IN @lt_ekko
    WHERE ebeln = @lt_ekko-ebeln.
ENDIF.

" ✅ BETTER — Use JOIN instead of FOR ALL ENTRIES
SELECT e~ebeln, e~ebelp, e~matnr
  FROM ekpo AS e
  INNER JOIN ekko AS h ON e~ebeln = h~ebeln
  INTO TABLE @DATA(lt_ekpo)
  WHERE h~bukrs = '1000'.

Summary: Code Pushdown Rules

Rule Description
1 Select only the columns you need (no SELECT *)
2 Filter at the database level (WHERE, not ABAP IF)
3 Use JOINs instead of nested SELECTs
4 Use aggregate functions (SUM, COUNT, AVG) in SQL
5 Use ORDER BY instead of ABAP SORT
6 Use CASE/COALESCE expressions in SQL
7 Use CDS Views for complex data models
8 Use AMDP for complex algorithms
9 Avoid SELECT * — specify exact fields
10 Check internal table before FOR ALL ENTRIES

Q48. What are User Exits, Customer Exits, BADIs, and Enhancement Points?

Answer:

These are mechanisms to extend or modify standard SAP behavior without modifying SAP source code.

1. User Exits (Oldest — Obsolete)

  • Empty subroutines in SAP standard code
  • Found in SD module (VOFM)
  • Example: USEREXIT_PRICING_PREPARE_TKOMK

2. Customer Exits

  • Pre-defined exit points with CALL CUSTOMER-FUNCTION in SAP code
  • Three types:
    • Function Module Exits (CMOD/SMOD): Implement logic in function modules
    • Screen Exits: Add custom subscreens
    • Menu Exits: Add custom menu items
  • Transaction: SMOD (find exits), CMOD (create projects)

3. BADIs (Business Add-Ins)

  • Object-oriented enhancement technique
  • Define an interface → Implement a class

Classic BADI:

  • Transaction: SE18 (define), SE19 (implement)
  • Can be multiple-use (multiple implementations)

New BADI (Enhancement Spot):

  • Fallback class concept
  • Filter-based execution
  • Transaction: SE18 → Enhancement Spot → BADI

4. Enhancement Points / Sections (Most Modern)

" Implicit Enhancement Points — exist at every include's start/end
" Explicit Enhancement Points — SAP-defined
" Enhancement Sections — Replaceable code blocks

" Implicit Enhancement (available everywhere):
ENHANCEMENT 1 Z_MY_ENHANCEMENT.
  " Custom code here
ENDENHANCEMENT.

How to find the right enhancement:

Method Description
Debug the standard transaction Set breakpoints, find where to add logic
Search for CALL CUSTOMER-FUNCTION In the standard code
Use SE18 to find BADIs Search by package or application component

Q50. What is BDC (Batch Data Communication)?

Answer:

BDC is a technique for automating data entry into SAP by simulating user transactions programmatically. It records the screens and fields a user would normally fill in.

BDC Methods

Method Description Speed Error Handling
Call Transaction Processes one transaction at a time Fast Inline (immediate)
Session Method Creates a batch input session processed later Slower Session-based (SM35)

BDC Recording

Use SHDB to record a transaction and generate ABAP code:

  1. Enter the transaction code
  2. Perform the steps manually
  3. SHDB records all screens and field values
  4. Generate ABAP program from the recording

BDC Code Example (Call Transaction Method)

DATA: lt_bdcdata TYPE TABLE OF bdcdata,
      lt_messages TYPE TABLE OF bdcmsgcoll.

" Fill BDC data (screen, field, value)
PERFORM bdc_dynpro USING 'SAPMM01' '0100'.     " Screen
PERFORM bdc_field  USING 'BDC_OKCODE' '/00'.     " OK Code
PERFORM bdc_field  USING 'RMMG1-MATNR' '100'.   " Material Number
PERFORM bdc_field  USING 'RMMG1-MBRSH' 'M'.     " Industry Sector

CALL TRANSACTION 'MM01' 
  USING lt_bdcdata
  MODE 'N'              " N=No display, A=All screens, E=Errors only
  UPDATE 'S'            " S=Synchronous, A=Asynchronous
  MESSAGES INTO lt_messages.

PART 9 — Database Management & Data Modeling

Q56. What is Normalization? Explain the Normal Forms.

Answer:

Normalization is the process of organizing database tables to reduce data redundancy and improve data integrity.

Normal Form Rule Example
1NF Atomic values (no repeating groups) No comma-separated values in a field
2NF 1NF + No partial dependency (all non-key columns depend on the FULL key) Split tables if column depends only on part of a composite key
3NF 2NF + No transitive dependency (non-key columns don't depend on other non-key columns) Move indirectly dependent columns to separate table
BCNF Every determinant is a candidate key Stronger version of 3NF

In SAP HANA context:

  • S/4HANA tends toward denormalization because HANA's in-memory, column-based storage handles redundancy efficiently
  • Example: ACDOCA (Universal Journal) combines data that was in 10+ tables in ECC
  • The performance benefit of avoiding JOINs outweighs storage costs in HANA
